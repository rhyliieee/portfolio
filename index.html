Systems I've built

Three automations from my current work in Philippine HRIS and payroll, where a missed message or a wrong number ends up on someone's payslip. Each one uses a pattern that applies in almost any business.

HRIS issue alerts that reach the right people

When an issue is raised for our HRIS, an automation sends a structured Lark message to the responsible team straight away: what happened, where, and who reported it.

Why it was needed. An issue only gets fixed once the right person knows about it. Relying on someone to notice and forward it is how things slip.

Where else it applies. This is the shape of a good customer enquiry workflow: a message comes in, it's routed to an owner, and nothing sits unseen in an inbox.

Built in Lark
  1. Issue raised
  2. Details captured
  3. Lark message sent
  4. Team picks it up

Requirements specs that draft themselves

A Lark automation generates the first draft of a System Requirements Specification from structured inputs, so every spec starts complete and in the same format.

Why it was needed. Writing specs from a blank page is slow, and every author structures them differently. A generated draft makes the important sections impossible to forget.

Where else it applies. The same idea powers reusable email templates, intake forms and SOPs: consistency is built in once instead of remembered every time.

Built in Lark
  1. Request logged
  2. Inputs structured
  3. Spec drafted
  4. Ready for review

Release items deployed to QA without waiting on a person

An n8n workflow deploys release items to our QA environment during each release cycle, so testers get what they need on time.

Why it was needed. Manual deployments in a busy release are slow and easy to get wrong, and every delay eats into the time left for testing.

Where else it applies. Nothing should reach a real customer untested. I build changes somewhere safe, test them, and only then switch them on.

Built in n8n
  1. Item ready for QA
  2. n8n workflow runs
  3. Deployed to QA
  4. Testing starts

Behind all three: testing as a habit

I set up automated tests, regression checks and quality gates in GitHub Actions, and I write runbooks for how systems are deployed and operated. That habit carries to any platform: try to break a workflow before a customer does, and write down how it works before anyone needs to ask.

How I'd start with any team

My process, not past client work

The order matters: fix what people feel first, then build what compounds.

  1. 1

    Map what's really happening

    Walk through every enquiry, request, form and handoff. Note where information is typed twice, forgotten, or chased by hand.

    You get: a one-page map of your systems and a short priority list.

  2. 2

    Make the critical path reliable

    Fix the flows people feel first: fast replies, a clear owner for every request, and nothing dropped, including after hours.

    You get: tested workflows and an SOP for each.

  3. 3

    Build what compounds

    Reusable templates, automations and email sequences that the team can update without me.

    You get: a template library and a map of every automation.

  4. 4

    Digitise the manual work

    Move paper forms, spreadsheets and repeated manual steps into connected systems that keep records consistent.

    You get: digital processes that are live, tested and documented.

Every phase ends the same way: tested before it goes live, written up as an SOP, and handed over so nothing lives only in my head.

What an SOP from me looks like

Short, specific and testable. This sample is written for a typical customer enquiry flow.

Try the checklist. Nothing goes live until every box is ticked.

Sample SOPVersion 1.0

New enquiry autoresponder

Purpose
Every new enquiry gets an on-brand reply within minutes and a named owner.
Trigger
A new message arrives from someone who isn't a customer yet.
Owner
Systems owner, reviewed monthly with the team lead.

Steps

  1. The auto-reply sends a greeting, the booking link and opening hours.
  2. The enquiry is tagged with the service it mentions.
  3. If there's no booking after 24 hours, the team gets a follow-up task.

Before go-live

4 checks left before go-live

If something breaks: switch the workflow off. Enquiries fall back to manual replies while it's fixed.

How I work

Give me an idea and a direction. I'll research the options, ask the questions that matter, build it, and follow through.

Test it before it touches a customer

I try to break every workflow in a safe environment first, including the odd cases like after-hours messages and duplicate contacts.

Measure instead of assuming

If a change is meant to save time or bring in more business, I check whether it did, and adjust when it didn't.

Write it down once

Every system I build ships with an SOP, so nobody has to rediscover how it works or depend on me to explain it.

Own it until it works

Once a project is agreed, I move it forward on my own and raise problems early, with a proposed fix attached.
