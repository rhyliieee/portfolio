Systems I've built

Three automations from my current work in Philippine HRIS and payroll, where a missed message or a wrong number ends up on someone's payslip. Each one uses a pattern a clinic runs on every day.

HRIS issue alerts that reach the right people

When an issue is raised for our HRIS, an automation sends a structured Lark message to the responsible team straight away: what happened, where, and who reported it.

Why it was needed. An issue only gets fixed once the right person knows about it. Relying on someone to notice and forward it is how things slip.

Where it fits a clinic. This is the shape of a good enquiry workflow in Podium: a message comes in, it's routed to an owner, and nothing sits unseen in an inbox.

Built in Lark
  1. Issue raised
  2. Details captured
  3. Lark message sent
  4. Team picks it up

Requirements specs that draft themselves

A Lark automation generates the first draft of a System Requirements Specification from structured inputs, so every spec starts complete and in the same format.

Why it was needed. Writing specs from a blank page is slow, and every author structures them differently. A generated draft makes the important sections impossible to forget.

Where it fits a clinic. The same idea powers reusable email templates, consult forms and SOPs: consistency is built in once instead of remembered every time.

Built in Lark
  1. Request logged
  2. Inputs structured
  3. Spec drafted
  4. Ready for review

Release items deployed to QA without waiting on a person

An n8n workflow deploys release items to our QA environment during each release cycle, so testers get what they need on time.

Why it was needed. Manual deployments in a busy release are slow and easy to get wrong, and every delay eats into the time left for testing.

Where it fits a clinic. Nothing should reach a real client untested. I build changes somewhere safe, test them, and only then switch them on.

Built in n8n
  1. Item ready for QA
  2. n8n workflow runs
  3. Deployed to QA
  4. Testing starts

Behind all three: testing as a habit

I set up automated tests, regression checks and quality gates in GitHub Actions, and I write runbooks for how systems are deployed and operated. That habit carries to any platform: try to break a workflow before a client does, and write down how it works before anyone needs to ask.

What an SOP from me looks like

Short, specific and testable. This sample is written for the enquiry flow in my plan.

Try the checklist. Nothing goes live until every box is ticked.

Sample SOPVersion 1.0

New enquiry autoresponder

Purpose
Every new enquiry gets an on-brand reply within minutes and a named owner.
Trigger
A new message arrives from someone who isn't a client yet.
Owner
Systems VA, reviewed monthly with the clinic manager.

Steps

  1. The auto-reply sends a greeting, the booking link and opening hours.
  2. The enquiry is tagged with the treatment it mentions.
  3. If there's no booking after 24 hours, front desk gets a follow-up task.

Before go-live

4 checks left before go-live

If something breaks: switch the workflow off. Enquiries fall back to manual replies while it's fixed.

How I work

Give me an idea and a direction. I'll research the options, ask the questions that matter, build it, and follow through.

Test it before it touches a client

I try to break every workflow in a safe environment first, including the odd cases like after-hours messages and duplicate contacts.

Measure instead of assuming

If a change is meant to save time or lift bookings, I check whether it did, and adjust when it didn't.

Write it down once

Every system I build ships with an SOP, so nobody has to rediscover how it works or depend on me to explain it.

Own it until it works

Once a project is agreed, I move it forward on my own and raise problems early, with a proposed fix attached.
